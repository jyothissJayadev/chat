# Architecture Baseline — Phase 0

Snapshot of the system as it exists today, before any rearchitecture work begins. Every later phase in the implementation plan diffs against this document. Do not edit this file to reflect in-flight refactor work — it's a frozen reference point, not a living doc (superseded, not updated, when Phase 7 cuts over).

## Intent model (current state, for Phase 1/2 grounding)

Today's routing is `state["intent"]: list[str]`, not a single label — the four valid intent strings are `context_related`, `direct_question`, `database_query`, `update_context` (see `app/deepinfra.py: Intent`, `_VALID_INTENTS`). Multi-label turns are already possible and already handled: `classify_intent_node` calls the classifier, then applies two deterministic guards (`guard_database_query`, `guard_split_intents`) before routing. `_route_intent` sends `len(intents) > 1` to `handle_split_intents_node`, which runs each requested branch concurrently via `asyncio.gather` and merges results. This is the exact mechanism the plan's Phase 1 `execute()` and Phase 2 `TaskSpec[]` are meant to generalize — it is not being built from scratch, it already exists in a narrower form.

There is no `DELETE_CONTEXT` equivalent today — `field_status` only moves forward (`unset` → `confirmed`/`assumed`/`skipped`), confirmed by `PartialContext`/`decline_field_node`/`save_project_node`. Matches the plan's note that this is new user-facing behavior, not a refactor.

## Freeze rule

Per the plan: no new fields added to `PartialContext.PROJECT_FIELDS`/`ROOM_FIELDS`, no new `ContextGraph` node types (`GraphNodeType`), no new LangGraph nodes in `app/graph.py`, until Phase 7 (Context Builder) exists to receive them. Any feature request that would require one of these gets logged and deferred, not implemented against the current model.

## Corrections vs. the original plan text

- **No gRPC transport exists.** The plan's table lists `app/grpc_server.py` as a current component; it isn't in the repo. Only SSE (`POST /chat` in `app/chat.py`) is wired up today. `run_chat_turn()` already yields transport-agnostic dicts, so this doesn't block anything — just don't assume a second transport is live.
- **`handle_split_intents_node` already exists and already works** the way Phase 1 describes wanting `execute()` to work (concurrent dispatch + merge) — this lowers risk on Phase 1/2, it's a generalization of a proven path, not new territory.
- **The `timeline` field's separate end-of-function handling** in `PartialContext.next_field_to_ask()` is deliberate (moderate-tier field asked last, after every room and `moreRoomsPending` are resolved), not a bug — it's commented as such in `models.py`. Phase 15's "structurally impossible to fall out of sync" framing is about a *different* class of fields (ones that could be added later and forgotten), not about `timeline` specifically, which is already correctly handled by design.
